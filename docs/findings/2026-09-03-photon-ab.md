# Findings — the Photon A/B, and why only two of its three rows count

**Date:** 2026-09-03
**Run:** Databricks job run `693303490917119` (`databricks_job.photon_ab`),
two arms on two job clusters, both **SUCCESS**. Phase 1's calibration slice
(2025-08-13, 24 hours) through Bronze → Silver → Gold, timed per layer.
**Method:** each arm's own `ArmMeasurement` JSON, written to
`/Volumes/almanac_dbx/burn/photon_ab/` and retrieved locally.

The §8.2 hypothesis was **pre-registered in the design doc before any
measurement** and is reproduced here unedited:

> Photon helps silver and gold materially, helps bronze little or nothing
> (bronze is almost all JSON parsing, which Photon covers only partially),
> and the blend may be a wash or a loss.

---

## What was measured

Both arms report `compressed_gb = 2.0124815106391907` — byte-identical, so
they processed exactly the same slice.

```json
arm_standard  {"photon": false, "bronze_seconds": 213.885,
               "silver_seconds": 63.385, "gold_seconds": 60.922}
arm_photon    {"photon": true,  "bronze_seconds": 180.623,
               "silver_seconds": 32.310, "gold_seconds": 42.125}
```

| Layer | Photon off | Photon on | Speedup | Verdict (threshold 1.10) |
|---|---|---|---|---|
| Bronze | 213.9 s | 180.6 s | **1.18x** | helped |
| Silver | 63.4 s | 32.3 s | **1.96x** | helped |
| Gold | 60.9 s | 42.1 s | 1.45x | **not usable — see below** |
| Sum of layers | 338.2 s | 255.1 s | 1.33x | — |
| Billed execution | 467 s | 380 s | 1.23x | — |

Both arms ran dbt to `PASS=23 WARN=0 ERROR=0 SKIP=0`.

---

## The hypothesis is falsified, on the leg it was most confident about

`hypothesis_holds` is **False**. It requires Bronze to come in at "no
material change", "hurt", or "no data", and Bronze measured **1.18x** —
above the 1.10 materiality threshold, so "helped".

The reasoning behind the prediction was that Bronze is almost all JSON
parsing, which Photon covers only partially. Two things about the actual
Bronze path are worth holding against that:

- Bronze here is `spark.read.text` plus two literal columns and a Delta
  write. It does **not** parse JSON at all — parsing is Silver's job
  (`payloads.parse_events`). So the premise of the prediction does not
  describe the code it was predicting about.
- Bronze is single-threaded on non-splittable gzip
  (`2026-09-02-bronze-is-single-threaded.md`), so a 1.18x gain is on one
  core, not on the cluster.

**The prediction was wrong for a reason the design doc could have caught
by reading `_land_bronze`.** Recorded as falsified rather than reworded,
per §13: the hypothesis is not edited after the result.

Silver at **1.96x** is the strongest result and the least surprising one —
it is the layer doing real columnar work (parse, normalize three eras,
shuffle for dedup, six quality rules, two writes).

## Why the Gold row is not usable

**Both arms shared one Unity Catalog metastore, concurrently.** The
catalog listing after the run is the evidence:

```
almanac_dbx.silver.events  EXTERNAL  abfss://silver@.../photon_ab_photon/clean
almanac_dbx.gold.dim_repo          MANAGED
almanac_dbx.gold.fact_pull_request MANAGED
almanac_dbx.gold.agg_repo_daily    MANAGED
```

Two independent faults, both visible in that listing:

1. **`register_silver_sources` uses `CREATE TABLE IF NOT EXISTS`.** The
   photon arm won the race, so `silver.events` points at
   `photon_ab_photon/clean` — meaning **the standard arm's dbt read the
   photon arm's data**, not its own. Its own Silver output at
   `photon_ab_standard/` was written and then ignored.
2. **`gold.*` are MANAGED tables both arms merged into at the same time.**
   The models are `incremental` with `merge`, so each arm's Gold work
   depended on what the other had already committed.

Bronze and Silver are clean — separate `--bronze-path`, `--silver-path`
and (since this run) separate staging dirs per arm, so those two rows
stand. Gold does not, and 1.45x should not be quoted.

**Not fixed here.** The fix is a per-arm dbt schema (and a per-arm source
schema), which changes what the arms write and therefore needs its own
run to produce a comparable number. Recorded as a defect in the harness
rather than silently dropped, and rather than shipping a fix whose effect
has not been measured — the same rule defect #8 established.

## The cost verdict is withheld, by construction

`dbus_consumed` is `0.0` in both arms: the job passes no `--dbus`, and
`_run_cost` is `num_nodes * usd_per_node_hour * wall_seconds/3600 +
dbus_consumed * usd_per_dbu`. With DBUs at zero, cost collapses to VM time
alone, so `paid_for_itself` would reduce to "Photon was faster" — and
since Photon's entire cost penalty **is** its DBU premium, that would
systematically favour Photon.

This is the design working as written: `compare` is a deliberate manual
step once the billing API carries per-run DBU totals, 24–48h later.
Running `compare` now would print a number the method cannot support, so
it has not been run.

**What is needed to close §8.2:** per-run DBU totals for both task runs
(`1063658033177813` photon, `719412933113624` standard) from the billing
system tables, then `photon_ab compare --usd-per-dbu 0.30
--usd-per-node-hour 0.474 --num-nodes 5`. The node rate is the measured
`D4ds_v6` westus3 figure behind STATUS's $2.370/cluster-hour, not the
0.249 placeholder in the module docstring's example.

## What the run also proved, incidentally

This was the first time Gold ran anywhere but a laptop and CI, and it
cleared four things at once:

- The `abfss://` URI fix works end to end — external tables created and
  read through.
- The explicit `--project-dir` fix works — dbt resolved its project on a
  workspace path.
- `dbt_session`'s `getOrCreate()` **does** return the cluster's live
  session and silently drop the warehouse/metastore configs, as
  `runner.py`'s docstring warns — and on a cluster with a real Unity
  Catalog metastore that is harmless. Previously unverified, now observed.
- `run_cli` reported **SUCCESS** on a normally-completing job task, which
  is exactly the case that used to report FAILED (defect #9).
